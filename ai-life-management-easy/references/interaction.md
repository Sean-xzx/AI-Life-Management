# 日常交互与日报接口

## 开始和深度

首次只问当前最重要的问题；用户已给信息则直接行动。需要背景时顺着当前任务补时间、责任、偏好，不显示完整档案清单。默认标准回复：一个下一步、完成标准、必要的一句理由。极简只保留行动与标准；深入增加证据与取舍。问法或表格仅在用户需要时展示。

## 自然表达

| 用户说 | 响应及记录变化 |
| --- | --- |
| 今天安排一下 | 结合已知责任与精力选一个重点，不凑满日程 |
| 现在该做什么 | 获取新时间，只检查接受的计划；没有时间工具不编造 |
| 记一下 | 按证据类别保存有关内容，不顺势布置任务 |
| 完成了 | 对象明确就记 user_report 与证据，模糊则确认对象 |
| 没做成 | 记录实际障碍，区分目标价值与方法尺度，不责备 |
| 计划变了 | 更新当前安排，取消失效待办，保留过去结果 |
| 纠正一下 | 更新同一字段或记录，不制造一个互相冲突的新事实 |
| 暂停或恢复 | 尊重选择；暂停后不排该目标，恢复先看新约束 |
| 我很累 | 减少负荷，允许今天主要恢复 |
| 帮我选 | 比较可选方案、维持现状与底线，权重由用户定 |
| 今天结束 | 全日信息→简短分析→明日一步→覆盖说明 |
| 回顾一周 | 看趋势及实际证据，不把日报拼接成冗长流水账 |
| 继续上次 | 读取已有资料或衔接摘要，补问变化而非重问全部 |
| 少问一点或详细解释 | 改回复深度，不重建档案 |
| 今天别催我或稍后提醒 | 记录 quiet_until 或 reminders_paused；未配置通知不能说已改通知 |

## 记录日期和安静设置

新事件仍经原 life_store.py 保存。as_of 使用 YYYY-MM-DD 或带偏移的 ISO 时间；录入时间与发生日期不同。用户补昨日结果时写昨日 as_of，不把所有事项归到录入当天。

安静偏好可保存 profile：key=reminders_paused、value=true、category=user_preference；或 quiet_until=带偏移时间。取消安静时使用新修订。日期不明的纯时间不要猜时区。

原助手会合并同一记录的当前状态。日报读取历史全日时间线并重建报告日期以前的背景，因此早期计划与中途修正仍然可见。基于用户资料的隐私与权限规则沿用原记录规范。

## CLI 与模型的分工

脚本 daily.py 的 clock 读取系统 UTC 并转换偏移；context 导出当天全部事件及相关背景，不截断；next 检查在本次调用时已接受且到点的安排，不提供后台服务。report 将规则预览或模型分析渲染成五段短报告，保存版本。

--offset 是明确的 UTC 偏移，如 +08:00；默认参数适合本项目的中文示例，不表示推断所有用户的时区。夏令时或移动地区须由宿主或用户提供当前正确偏移。脚本不依赖 Windows 缺失的时区数据库。

## 模型日报 JSON

先完整读取 context，然后形成分析文件。每条 evidence 引用 context 中事件的 event_id；基于旧目标的建议可引用 baseline_sources。输出结构如下，字段只在需要时填写：

```json
{
  "overview": {"text":"今日围绕口语目标进行了尝试并调整时间预算。", "evidence":["e-result","e-correction"]},
  "progress": [{"text":"你报告已录30秒，60秒目标仍在进行中。", "kind":"user_report", "evidence":["e-result"]}],
  "interpretation": [{"text":"新的时间预算可能需要更短练习；实际余量仍待确认。", "kind":"estimate", "evidence":["e-correction"]}],
  "tomorrow": [{"text":"若时间允许，先用5分钟补一个例子并保存试录。", "kind":"suggestion", "goal_id":"g-speaking", "evidence":["e-result","e-correction"]}]
}
```

示例是格式说明，不能直接拿示例 ID 写入真实日报。progress 的 fact 只能引用 confirmed_fact/observed_result；user_report、decision 按对应来源。interpretation 明确为 estimate；tomorrow 为 suggestion。关联目标时必须填 goal_id，暂停或停止的目标不能继续安排。

report 检查长度、条数、ID存在、类别与显式目标状态，但不能验证文字是否忠实或因果是否成立。使用者仍需逐项核对，不能把引用ID当科学证明。不提供模型文件时只输出明确标注的规则预览。

## 纠正与详细模式

`context.current_sources`给出每个记录当前事件版本；`historical_only_evidence`包括已被替换或依赖失效的事件。它们不能支持当前概况、进展或建议。若需要比较“早先报告→后来纠正”，放在interpretation中，设置`historical:true`，渲染为历史复盘；不要通过这一标记把旧数值变成现行依据。

`invalidated`需要重算；`untracked_derived`表示没有足够依赖声明，自动检查不保证这些旧记录仍适用。估算引用来源事件的`depends_on`写法见[记录规范](../../ai-life-management/references/records.md)。用户改值后重新计算合计，更新当前计划，而不只在日报末尾再追加一句相反意见。

默认`--layout short`沿用600字符正文预算。用户明确要求完整报告或各方面行动建议时使用`--layout detailed`：单行至多600字符、正文至多8000字符；progress至多16条、interpretation10条、tomorrow6条，可另加至多16条`action_plan`。这些是工具预算，不要求凑满；遵守实际请求范围。

```json
{
  "overview":{"text":"截至午后的实际记录与晚间建议分开。","evidence":["e-current"]},
  "progress":[],
  "interpretation":[],
  "tomorrow":[],
  "action_plan":[
    {"area":"恢复","text":"按当前精力安排一次短休息，完成后反馈感受。","kind":"suggestion","evidence":["e-current"]},
    {"area":"学习","text":"在现有空档完成一项小交付并保存。","kind":"suggestion","goal_id":"g-learning","evidence":["e-goal"]}
  ]
}
```

area是至多40字符的领域标签，只用于action_plan；示例ID必须换成实际上下文中的来源。所有模式沿用证据分类与暂停目标限制。日期检查点出现在next的`date_checkpoints`，不冒充具有具体时刻的提醒；未接受的AI建议不催。

## 保存和修订

report --write 保存到资料目录 reports/YYYY-MM-DD.md 及同名JSON；改变后将旧版本保存在 reports/history。相同内容不重复制造版本。该目录只是派生报告，不回写核心日志或快照；原资料可重生成日报。报告文件和时间工具执行不等于已经配置晚上通知。

写入时同时保护报告与记录版本；存在记录写锁或context已过期时停止，重读并重新分析。不同版式的旧报告仍可核对和归档；手工编辑的内容不能静默覆盖。

## 十个虚构交互示例

1. “不知道做什么”：先问最挂心的一件事；用户尚未回答时不给虚构计划。
2. “目标是英语，只有15分钟”：给一段小练习与保存标准，不先问年龄职业。
3. “到点但正在忙”：确认计划变化，提供稍后或取消，不责备。
4. “完成了但无文件”：记用户报告，明确未独立检查。
5. 全天资料充分：比较早期计划、中午调整和晚间结果，提一个与证据相连的明日行动。
6. 只有一条资料：短日报，说明覆盖不足；不推测全天时间。
7. 补遗漏的昨日结果：以昨日 as_of 记录，修订昨日日报。
8. 暂停后再打开：不提醒暂停事项，只处理当前需求。
9. 无时间或提醒工具：采用用户时间并说明依据；通知未配置。
10. 换软件：生成五项衔接摘要，由用户复制，接收方先用已有信息。

这些是设计示例，不是实际用户反馈或全部平台测试结果。
